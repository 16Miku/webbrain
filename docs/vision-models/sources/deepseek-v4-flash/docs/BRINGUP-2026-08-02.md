## Quantized-backward finding

The 273.86 GiB `sgl-project/DeepSeek-V4-Flash-FP8` checkpoint loaded successfully across
four H200s. Transformers placed 11/12/12/13 module groups on devices 0/1/2/3. The initial
RunPod PyTorch 2.8/Triton 3.4 image was too old for the released UE8M0 kernel; upgrading the
DeepSeek environment to PyTorch 2.11/Triton 3.6 fixed the forward kernel.

The decisive micro-test then showed that the official `finegrained-fp8` Triton op has no
registered autograd formula. It can execute a finite forward but raises when asked for the
input gradient. A frozen language model still needs input gradients to train the visual
projector, so the released FP4/FP8 and repacked FP8 checkpoints are inference-only for this
training design.

## Six-H200 backward gate

A fresh RunPod Secure Cloud node with six 143,771 MiB H200s and full `NV18` peer links
reconstructed the same checkpoint. Its integrity scan passed with 46 shards, 35,020 tensors,
542.011 GiB of safetensor files, no partial files, and no quantization-scale tensors.

The pinned Transformers V4 implementation keeps RMSNorm weights in FP32, but its norm return
path allowed the FP32 weight multiplication to promote BF16 activations. That failed at the
next BF16 projection. The routing-aware wrapper now installs a narrow dtype-boundary hook:
norm computation and weights remain FP32, while the returned activation is restored to the
input dtype. A focused regression test passes in the H200 environment.

## Watchdog correction

The original remote watchdog sequenced `sleep` and the stop request unconditionally. RunPod's
SSH teardown could terminate the `sleep` child, after which the shell immediately issued the
stop request. The script now uses `sleep && stop`, detaches into a new session, and accepts
durations such as `30m` and `4h`. For this validation, the API-key-bearing deadline was moved
to a local macOS launch job so no RunPod key had to be persisted inside a resumed container.

The first local guard was still a blind rolling 30-minute timer. On the 100k data/cache run,
the refresh missed its deadline and stopped a healthy pod. The replacement
`runpod_verified_work_guard.sh` re-checks the exact approved processes at expiry, tolerates
transient API or SSH failures, and enforces a separate absolute budget deadline. It does not
persist the RunPod key; each API action reads it from macOS Keychain only when needed.
