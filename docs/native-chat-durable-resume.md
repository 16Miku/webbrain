# Native chat durable resume verification

An ongoing conversation must be able to wait through a browser alarm and worker restart without sending an already delivered reply again. A running resume job now creates a separate future successor. The scheduler records the actual running predecessor privately; repeated future jobs with the same intent still coalesce. That predecessor relationship also survives storage restoration.

For supported native Telegram conversations, the chat kernel stores a bounded delivery receipt only after an independently observed outgoing message matches the guarded recipient, exact authored body, and a new native message ID. The receipt binds the genuine user turn, exact original task digest, canonical peer, page URL, originating run/action, message ID, and body digest. It stores no transcript or full message body. A new user turn with identical wording cannot inherit it.

Native Telegram sends and delivery acknowledgement require the verified latest viewport, not merely the bottom of an older virtual slice. A shared `mounted_native_id_floor` validates all mounted IDs and peers and retains the highest 200 numeric IDs, including empty and media-only rows. The private floor does not claim full-history completeness and cannot be lowered by the authored-message cache. The one-use dispatch token binds that baseline; structured `chat_send` also refuses any difference between its original observation and the actual recipient probe before pending state is created or persisted. Incomplete, changed or wrong-thread evidence requires fresh observation, without rebasing the send.

A same-task alarm can finish from that receipt only after reading the current native conversation again. The same message must still exist with the same authored body and peer, the composer must be empty, and no pending outbound message, OTP pause, unrelated current page action, or verification debt may remain. A provider, task, recipient, or page change during the read invalidates it. Internal terminal reads never consume incoming deltas: a newly arrived question blocks completion until the model explicitly observes it. The normal `done` bookkeeping step preserves its own freshly verified proof; a later tool invalidates that sequence. This does not add a fictional action to the resumed run's execution counter.

An unanswered permission or ordinary clarification is recovered from its live Agent entry when the panel reopens, even after replay acknowledgement. The descriptor remains bound to the current request, run, task, provider and steering revision; settled entries, Stop, replacement tasks and worker loss cannot revive it. When a run ends (finished, failed or stopped), the panel closes the cards it still showed: a permission card is removed and a question is locked, so a card left on screen after Stop can no longer be clicked; a scheduled task's cards stay with that task. Hydration rechecks current state, preserves the original deadline and never answers or renews the question. Accepted mid-run corrections wake obsolete permission waits without recording a grant or dispatching the earlier action, then continue through the normal steering boundary. The paired owned-fixture suites contain 54 hydration and 22 permission-steering checks; this is UI and control-flow proof, not native delivery or external-service endurance proof.
